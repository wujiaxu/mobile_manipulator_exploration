## Upstream Runtime Model

FKIE starts the planner with:

```text
fkie_nbv_planner/launch/run_planner.launch
```

Important defaults:

```text
robot_ns: robot
world_frame: world
nbv_yaml_file: nbv_planner_freespace_fast
```

The planner node is launched under the robot namespace:

```xml
<node name="fkie_nbv_planner"
      pkg="fkie_nbv_planner"
      type="nbvplanner_node"
      ns="$(arg robot_ns)">
```

Inside `NBVPlanner.cpp`, the action server name is:

```cpp
planning_as_(nh_, "nbv_rrt", ...)
```

Therefore the default action name is:

```text
/robot/nbv_rrt
```

for `robot_ns:=robot`.

## Planner Action

File:

```text
third_party/fkie-nbv-planner/action/NbvPlanner.action
```

Goal:

```text
Header header
fkie_measurement_msgs/BoundaryPolygon current_boundary
fkie_measurement_msgs/MeasurementEstimation estimations
bool arm_in_prepacked
```

Result:

```text
geometry_msgs/PoseStamped[] goals
bool request_base_pose
geometry_msgs/PoseStamped goal_pose_3d
bool complete_exploration
int16 explored_boundary_id
```

Feedback:

```text
empty
```

Meaning:

- `goals`: arm/camera view poses returned when the robot base can stay in place.
- `request_base_pose`: true when the planner cannot find an arm-reachable NBV
  and asks the base to move.
- `goal_pose_3d`: frontier/base-related 3D pose when `request_base_pose` is true.
- Paper behavior detail for mobile-base fallback: when the final target EEF pose is not reachable, the base target should be generated by projecting the farthest suitable node on the RRT branch toward that EEF target onto the ground, not by projecting the unreachable final target directly.
- `complete_exploration`: true when no frontier or useful NBV remains.
- `explored_boundary_id`: boundary id that was explored.

## Required Input Topics

Inside the planner node, local subscriptions are:

```cpp
camera_pose_sub_ = nh_.subscribe("camera_pose", ...)
octomap_sub_ = nh_.subscribe("octomap", ...)
robot_footprint_sub_ = nh_.subscribe("robot_bbx", ...)
```

`run_planner.launch` remaps:

```xml
<remap from="camera_pose" to="camera_pose"/>
<remap from="octomap" to="octomap_full"/>
<remap from="/$(arg robot_ns)/robot_bbx"
       to="/$(arg robot_ns)/$(arg robot_ns)_mbf/global_costmap/footprint"/>
```

For `robot_ns:=robot`, expected upstream topics are:

```text
/robot/camera_pose
/robot/octomap_full
/robot/robot_mbf/global_costmap/footprint
```

The README describes the same interfaces without always including namespace:

```text
octomap_full
/realsense/depth/points2
camera_pose
${robot_ns}_mbf/global_costmap/footprint
```

## Current Project Topic Mapping

Our current baseline publishes:

```text
/octomap_full
/realsense/depth/points2
/camera_pose
/mobile_manipulator_mbf/global_costmap/footprint
```

This is compatible in message type, but not exactly compatible in namespace.

Options:

1. Launch the ported planner without a robot namespace.
2. Remap our current topics into the namespace expected by the planner.
3. Change the port to use explicit parameterized topic names.

Recommended for ROS 2 port:

- Use explicit parameters:
  - `camera_pose_topic`
  - `octomap_topic`
  - `robot_footprint_topic`
- Default them to our current topics.

## FKIE Measurement Messages

The planner action depends on `fkie_measurement_msgs`, from:

```text
third_party/fkie_environmental_measurements/fkie_measurement_msgs
```

Minimum messages needed by the NBV planner:

`BoundaryPolygon.msg`:

```text
int16 id
string source_type
float32 min_height
float32 max_height
geometry_msgs/PolygonStamped polygon
```

`MeasurementEstimation.msg`:

```text
Header header
float32 grid_size
fkie_measurement_msgs/MeasurementEstimationValue[] values
```

`MeasurementEstimationValue.msg`:

```text
float32 x
float32 y
float32 z
float32 mean
float32 variance
```

The FKIE repo also references `RequestBoundaryPolygons.action` as a way to get
example exploration boundaries and measurement estimations from their
environmental-measurements stack.

For our first reproduction pass, we can avoid porting their full measurement
server by creating a small ROS 2 package with only these message/action
definitions plus a simple request client that sends a fixed boundary and empty or
synthetic estimations.

## Port vs Docker Bridge Decision

Recommendation: start with a ROS 2 native port, not a ROS 1 Docker bridge.

Reasoning:

- Our robot execution stack is already ROS 2 Humble.
- We already publish the planner inputs as ROS 2 topics.
- ROS 1 actionlib bridging for a custom action plus custom measurement messages
  would add a second message-definition and bridge maintenance problem.
- The planner algorithm itself is C++ and can be ported mechanically:
  - `ros::NodeHandle` -> `rclcpp::Node`
  - `actionlib::SimpleActionServer` -> `rclcpp_action::Server`
  - ROS 1 messages -> ROS 2 messages
  - `tf` uses -> `tf2_ros`
  - package build -> `ament_cmake`

Docker remains useful for:

- verifying the original Noetic package builds,
- comparing parameter defaults,
- running original examples if needed.

Docker is not the best first runtime path for our Isaac reproduction because the
planner needs live custom actions, OctoMap, TF, and robot execution integration.

## Proposed Next Implementation Milestone

Create a ROS 2 package set:

```text
mobile_manipulator_fkie_msgs
mobile_manipulator_fkie_nbv
```

`mobile_manipulator_fkie_msgs`:

- Define ROS 2 equivalents of:
  - `BoundaryPolygon`
  - `MeasurementEstimation`
  - `MeasurementEstimationValue`
  - `NbvPlanner.action`

`mobile_manipulator_fkie_nbv`:

- Start as a minimal ROS 2 wrapper/port of FKIE planner interfaces.
- First goal:
  - subscribe to `/octomap_full`, `/camera_pose`, and footprint,
  - accept one `NbvPlanner` action request,
  - validate all required data exists,
  - return a deterministic placeholder candidate inside the boundary.
- Then port the actual FKIE RRT/gain code incrementally behind the same action
  interface.

Reason for placeholder first:

- It tests all ROS 2 action, message, frame, and execution plumbing before
  spending time porting the full algorithm.
- It gives a stable target for Nav2/MoveIt execution adapters.
